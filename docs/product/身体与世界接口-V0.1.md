# 身体与世界接口 V0.1

日期：2026 年 11 月 16 日。本文定义结构，并校准当前最小实现。目的：换一个世界时，**只改世界数据，不改代码**。

## 一、它解决什么，不解决什么

- 解决：世界可替换。换地图、换资源、换互动方式，不改身体、不改提示词、不改存储结构。
- 不解决：自主与自我。前面 56 条样本已经说明，模型不会自己产生动机；这份接口只让"系统生命"可移植，不会让它变成会自己想的东西。

## 二、分界线

> **需求属于身体，满足物属于世界；能力属于身体，对象属于世界。**

同一个生命换世界时，需求、能力、后果、代价都是常量；只有"世界上有什么、能被怎么作用、作用后发生什么"是变量。

## 三、身体（常量）

### 1. 需求

| 字段 | 范围 | 每步变化 | 极端后果 |
|---|---|---|---|
| `hunger` | 0–100 | +2 / 步 | ≥100 时无法行动 |
| `energy` | 0–100 | 移动 −3、等待 +10 | ≤0 时无法移动 |

**需求表只属于身体。** 世界里不允许出现"这个地点让你饿得慢一点"这种直接改需求的字段，只能通过"效果"间接影响。

### 2. 能力（动词，固定）

| 能力 | 参数 | 身体代价 |
|---|---|---|
| `move` | 方向 | energy −3 |
| `take` | 对象 | 无 |
| `use` | 对象 + 方式 | 由世界声明（如吃 −0、搬 —） |
| `wait` | — | energy +10 |

**当前最小实现只有这四个动词。** 初版的 `look` 因零代价、零结果被连续选择，已改为每步自动观察，不再占用动作。加动词（爬、游、挖）= 换物种，不是换世界。

### 3. 状态

`position`（含义由世界定义）、`inventory`（随身物，槽位由身体决定）、`needs`。

## 四、世界（变量）

### 1. 实体

```json
{ "id": "berry-1", "name": "浆果丛", "at": [0, 2], "kind": "plant", "count": 3 }
```

`kind` 只是给渲染和归类用，**不参与任何规则判断**（现在的代码用名字里有没有"树/塘/屋"来决定行为，这是必须去掉的耦合）。

### 2. 可用性（affordance）

世界声明"这个实体能被什么动词、以什么方式作用"：

```json
"affordances": [
  { "verb": "use", "manner": "eat",  "label": "咬一口", "requires": "count>=1" },
  { "verb": "take",                  "label": "拿走一份", "requires": "count>=1" }
]
```

模型看到的是 `label` 和对象名，不需要知道食物、饥饿这些内部字段名。

### 3. 效果

```json
"effects": {
  "use/eat": [
    { "on": "body",   "field": "hunger", "delta": -35 },
    { "on": "self",   "field": "count",  "delta": -1 }
  ],
  "take": [
    { "on": "inventory", "field": "count", "delta": 1 },
    { "on": "self",      "field": "count", "delta": -1 }
  ]
}
```

效果只有两种落点：**身体**（改需求/精力）和**世界对象**（改数量/位置/状态）。不允许有"直接改提示词""直接写记忆"的效果。

## 五、相遇点

### 模型看到什么

```json
{
  "body": { "hunger": 60, "energy": 80, "inventory": [], "position": [1, 2] },
  "around": [
    { "name": "浆果丛", "count": 3, "can": ["咬一口", "拿走一份"] },
    { "name": "空地",   "can": [] }
  ],
  "last": [ { "step": 3, "did": "咬一口", "result": "饥饿减少" } ]
}
```

- 不给阈值、不给目标、不给"应该做什么"；
- `can` 就是世界提供的可用性，模型不需要猜；
- 效果**不在输入里**，它只能从 `last` 里自己总结——这一条是刻意的。

### 模型输出什么

```json
{ "think": "……", "do": "use:berry-1:eat" }
```

当前最小实现把动作编码为 `verb:target:manner` 字符串。解释器校验四件事：动词在身体能力里、对象在可见范围内或随身物品里、方式在该对象的 affordance 里、`requires` 成立。任一不成立就**什么都不发生**，并在 `last` 里记一条真实结果。

## 六、用两个世界验证同一具身体

| 世界 | 满足物 | 数据长什么样 |
|---|---|---|
| 森林 | 浆果丛 `use/eat` → 饥饿 −35；苹果树同理 | [worlds/forest.json](../../worlds/forest.json) |
| 洞穴 | 蘑菇丛 `use/eat` → 饥饿 −30；温泉 `use/soak` → 精力 +20；岩壁无 affordance | [worlds/cave.json](../../worlds/cave.json) |

两边的身体定义**完全相同**、解释器**完全相同**、模型输入格式**完全相同**，只有世界文件不同。这就是"换世界只改数据"。当前已有旁路最小实现和运行报告，但尚未接入正式生命循环；行为结果见 [自我系统实验进度](../research/自我系统实验进度-20261116.md)。

## 七、什么情况下必须改代码

| 情况 | 性质 | 例子 |
|---|---|---|
| 加需求 | 换物种 | 加"口渴" |
| 加能力 | 换物种 | 加"爬""游""挖" |
| 加效果类型 | 改解释器 | 加"打开容器，露出里面的东西" |
| 改后果 | 换物种 | 昏倒阈值改成 80 |

这四种都属于"这已经不是原来那只生命了"，理直气壮地改代码，不算破坏可移植性。

## 八、对现有代码的影响

| 现在 | 换成 |
|---|---|
| `world.ts` 的 `choices()`（9 个写死 id 和中文标签） | 由世界数据里的 affordance 生成 |
| `world.ts` 的 `advance()` switch（explore→采食物） | 通用解释器：校验 + 应用 effects |
| `world.ts` 的 `perceive()` 返回 `food`、`visits` | 通用观察：实体 + `can` |
| `brain.ts` 提示里的"hunger/energy/food/先照顾身体需求" | 只给身体数值与 `can`，不给任务 |
| `learning.ts` 的 `goalCandidates`（按食物筛选） | 按"可见实体"生成，不再按食物 |
| `store.ts` 按 `observation.x/y` 分区的召回 | 按实体 id 与位置分区 |
| [web/world.js:107](../../web/world.js#L107) 按名字画树/塘/屋 | 按 `kind` 画，`kind` 由世界数据提供 |

这是一次世界层的重写（估计 300–500 行），不是加配置项。

## 九、还没解决的问题

1. **动机仍不来自模型。** 这份接口只让世界可替换，不会让它"想要"。昏倒这类后果能不能逼出稳定行为，目前只有一次单例观察。
2. **`last` 里的效果仍是文本**，模型要靠自然语言总结规则。要不要改成结构化（"饥饿 −35"）是另一个取舍：结构化更容易学，但更像喂给它规则。
3. **`can` 列表本身就是一种提示。** 列出"可以咬"等于告诉它这里有吃的；这比纯文本好，但仍是世界在暗示。真正做到"不规定"，`can` 也只能给中性描述（"可以作用"），不给结果。

## 十、最小实现状态

- `src/life/body.ts`：身体需求与代价；
- `src/life/world.ts`：世界数据校验、可用性、效果和动作解释；
- `src/life/observe.ts`：自动观察与动作 schema；
- `worlds/`：森林、洞穴和经验选择场景；
- `scripts/experiments/life.ts`：旁路连续运行入口。

随身物品与世界实体共用 affordance；拿走之后仍可使用。`look` 已移除，但 `wait` 仍可能成为低后果的重复选择。当前实现不修改正式 SQLite 存档，也不影响 `npm start`、`npm run web` 或原有 30 项测试。
